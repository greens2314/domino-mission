## 1. 遊戲定位

《骨牌任務》是一款將實體積木與骨牌專案演練轉為線上操作的 3D 專案管理體驗遊戲。學生在固定預算、有限採購次數與倒數時間下，規畫、採買、搭建、詢問客戶、取得測試車、演練並正式驗收。

遊戲不設計分數、排名或全班進度牆。唯一的專案成功判準是：**在 60 分鐘內送交正式驗收，且驗收一次成功。**

成本與時間不是計分項目，而是讓學生體會「為節省成本或時間而少做確認、少做演練，可能使專案最終失敗」的決策壓力。

## 2. 教學目標

學生完成活動後，應能具體反思：

1. 需求模糊時，主動向客戶釐清的重要性。
2. 範疇、時間、成本三者如何相互拉扯。
3. 為何採購、演練與重工都屬於專案成本。
4. 為何「看起來完成」不等於「通過驗收」。
5. 團隊在時間壓力下如何分工、溝通與作出取捨。

## 3. 非目標與邊界

- 不建立教師控制台、全班進度牆、排行榜、分數或角色分工系統。
- 不使用隨機的真實 3D 物理引擎；以可預測、可驗證的規則判定驅動 3D 演練與驗收動畫。
- 不提供系統主動提示、標準答案、建議問題或失敗診斷給學生。
- 不處理學生上傳；學生自行下載驗收 PDF，繳交至既有課程系統。
- 不建立帳號或雲端後端。進度僅以瀏覽器本機儲存（localStorage）暫存。

## 4. 教室活動流程

| 階段 | 建議時間 | 學生行為 | 系統狀態 |
| --- | ---: | --- | --- |
| 教師說明 | 5 分鐘 | 聽取情境、規則與繳交方式 | 尚未開始 |

## 5. 視覺與操作原則

### 5.1 畫面風格

- 成熟手繪 3D 桌遊感：深藍、米白、木質工作桌與飽和積木色為主色，避免幼兒化風格。
- 以木質桌遊框架、深藍資訊列、暖色格板、彩色積木與骨牌為全站美術方向；所有素材須以同一風格重新產生並實際使用。
- 主畫面為可旋轉的 3D 工地；積木、骨牌與小車皆呈現立體模型。
- 提供鏡頭旋轉、縮放與平移，讓學生從不同角度檢查通道、距離與堆疊高度。
- 使用淡格線作為施工輔助，但**不可**對學生揭露「1 格等於 1 個設計單位」的換算。
- 提供自由使用的尺規與高度量尺，讓學生自行量測任務書以 cm 表述的要求。

#### 5.1.1 美術參考規格

以教師提供的參考圖作為全站視覺語言，採用「精緻桌遊插畫＋圓角立體玩具」風格，而非極簡扁平 UI 或寫實工程模擬。所有新產生素材必須符合以下規格：

| 元件 | 視覺規格 |
| --- | --- |
| 整體場景 | 深藍毛氈或皮革感外框搭配暖棕木桌，中央為暖米色施工格板；四角可有低干擾的植物、尺規或圖紙裝飾。 |
| 頂端資訊列 | 深藍底、厚實圓角米白資訊卡、粗體深藍繁體中文；預算與時間以彩色進度條呈現。 |
| 積木 | 高飽和紅、藍、黃、綠為主，具玩具塑膠質感、圓角、積木凸點與柔和陰影。 |
| 骨牌 | 直立彩色骨牌，具清楚白色點數與邊緣高光；連鎖方向以橘紅色箭頭或動畫顯示。 |
| 操作按鈕 | 大型圓角按鈕，黃＝需求／工具、紅＝演練、綠＝整合測試、藍＝正式驗收；顏色以功能區分，不代表分數。 |
| 3D 視角 | 使用介於俯視與等角視角的桌遊攝影機，讓高度、門洞與骨牌方向可辨識；避免第一人稱或寫實工程軟體視角。 |
| 字體與文字 | 所有系統文字採可編輯繁體中文；不可將會變動的時間、預算、小組名稱或提示文字畫死在圖片內。 |
| 動畫 | 小車行進、骨牌倒下、材料選取與按鈕回饋皆採短、清楚、可重複的動畫；不得以華麗動畫掩蓋驗收結果。 |

參考圖僅用於視覺風格，不複製其文字、版面內容、按鈕功能或任務解法。遊戲仍以本規格書定義的 60 分鐘、單次正式驗收、無局部演練與無分數排名為準。

### 5.2 主畫面配置

1. **頂端列**：小組名稱、開始時間、目前時間、剩餘時間、已花費、剩餘預算、採購次數。
2. **左側面板**：任務書、商店、現有庫存、尺規／高度量尺、採購紀錄。
3. **中央工地**：可旋轉、縮放的 3D 施工板、起點、車道與可拖放區域。
4. **右側面板**：已解鎖小車、全程演練、正式驗收等依狀態顯示的操作。
5. **底部**：活動紀錄提示，例如「已完成第 2 次採購」；不可提供解題提示。

### 5.3 3D 施工板與鏡頭規格

- 內部以 48 × 28 格平面網格與垂直高度層管理物件；此數值僅供程式實作，不對學生顯示。
- 物件可在 3D 工地中拖放、旋轉 90 度與垂直堆疊。
- 每塊積木高度為 1 個內部設計單位；堆疊高度以 3D 模型及高度標示共同呈現。
- 所有積木、骨牌均由學生逐一放置，不能一鍵鋪設或半自動生成。
- 骨牌需設定方向；方向、間距與高度落差必須符合後續的連鎖規則。
- 3D 模型只負責操作與視覺呈現；格位、旋轉、占地與高度仍寫入規則引擎，由規則引擎決定演練與驗收結果。

### 5.4 UIUX 驗收原則

本遊戲的 UIUX 不是裝飾，而是教學體驗的一部分。學生應把注意力放在專案決策，而非猜測如何操作系統。

| 面向 | 必須達成的體驗標準 |
| --- | --- |
| 資訊層級 | 畫面第一層固定顯示小組名稱、剩餘時間、已花費／剩餘預算與採購次數；3D 工地為視覺中心。 |
| 操作流程 | 明確呈現「規畫 → 採購 → 施工 → 取得小車 → 演練 → 正式驗收」；當前可進行的下一步必須易於辨識。 |
| 材料操作 | 同時支援拖曳放置與「選取材料後點選位置」；學生可選取已放置物件進行移動、90 度旋轉、堆疊或收回。 |
| 3D 鏡頭 | 提供旋轉、縮放、平移控制與首次使用的短提示；鏡頭操作不可改變施工資料。 |
| 選取回饋 | 被選取物件須有清楚外框、占地預覽、旋轉方向與高度資訊；非法位置須立即以非解題式訊息說明。 |
| 高風險操作 | 演練、正式驗收與收回材料皆須顯示後果與確認動作；正式驗收按鈕必須明確標示「僅 1 次」。 |
| 教學公平性 | 系統只提示操作、資源與狀態，不主動建議提問、不提供標準答案、不標示演練失敗原因。 |
| 螢幕適配 | 以 1366 × 768 教室筆電為最低優先畫面；主要操作不可依賴橫向捲動或被折疊遮住。 |
| 無障礙與容錯 | 所有主要按鈕需有文字標籤、鍵盤焦點與足夠對比；拖曳失敗時可改用點選放置。 |

每次功能完成後，至少需實測以下流程：輸入小組名稱、採購、3D 放置與旋轉、取得小車、全程演練、正式驗收成功／失敗、時間到期與驗收 PDF 下載。

## 6. 專案任務書

遊戲開始時，施工板完全空白；系統不預先提供柱子、門、骨牌、階梯或鑽石陣。

學生需以採購後的材料完成下列成果：

| 類別 | 任務要求 |
| --- | --- |
| 門 | 建造 2 個門；兩門之間距離須至少 10 cm。 |
| 柱子 | 建造 2 根柱子；每根高度須大於 6 cm。 |
| S 型路徑 | 排出可連鎖倒下的 S 型骨牌路徑。 |
| 骨牌階梯 | 建造精確 8 層的骨牌階梯；可中空，不要求實心。 |
| 鑽石陣 | 排出完整、填滿的 10 × 10 菱形骨牌陣。 |
| 最終效果 | 小車通過兩門、碰倒指定起始骨牌；連鎖反應需依序完成 S 路徑、8 層階梯與整個鑽石陣。 |

### 6.1 材料使用限制

- 門與柱子：只能使用積木，不可用骨牌支撐或混搭。
- 骨牌：只能用於連鎖反應，不可拿來建門或柱子。
- 積木尺寸可以混用於同一座門或同一根柱子。
- 鑽石陣為「填滿」要求；不得以空心輪廓替代。

### 6.2 10 × 10 菱形的判定模板

內部以 10 列、共 60 枚骨牌的填滿菱形模板檢驗，列數由上而下為：

```text
2 / 4 / 6 / 8 / 10 / 10 / 8 / 6 / 4 / 2
```

此為程式驗收規則；學生只看到「完整填滿的 10 × 10 菱形骨牌陣」的任務敘述與尺規工具，不看到內部座標或模板。

- 每張訂單可包含多種材料與多個數量。

- 付款後不可退款；即使材料未使用，成本仍保留在紀錄中。
- 購買後材料加入庫存；拖入施工板時扣除可用庫存；從板上移除時回到庫存。
- 取得測試小車不是採購，不計入採購次數與成本。

## 8. 需求釐清與客戶互動

### 8.1 教師即客戶

- 學生可在整場遊戲中最多提出 **3 次正式需求釐清**。
- 問題由學生自行形成，直接向教師口頭詢問。
- 回答由教師依課堂設計自行決定與口頭回覆；系統不記錄問題、回答或教師判斷。
- 系統不得預設「建議提問」、提示學生應詢問何事，或主動顯示隱藏驗收條件。

### 8.2 測試小車授權

- 起始時不提供小車。
- 學生必須主動向教師取得測試授權；教師在「客戶授權碼」欄位輸入 `car666`。
- 授權碼輸入成功後，免費解鎖 1 台測試小車。
- 小車可拖到施工板供學生目測尺寸與通行空間，但靜置時不會自動行駛。
- 授權碼不可出現在學生畫面說明、採購紀錄、驗收 PDF 或一般操作紀錄中。

## 9. 演練與正式驗收

### 9.1 演練

- 未取得小車前，不顯示「全程演練」與「正式驗收」按鈕。
- 取得小車後顯示「全程演練」與「正式驗收」按鈕；**不提供局部演練**。
- 按下全程演練時，必須先出現確認視窗：

  > 全程演練會使被觸發的骨牌倒下。演練後須由小組自行逐一重新排列與扶正；系統不會自動復原。是否已完成小組確認？

- 確認按鈕文字：`小組已確認，開始演練`；另有取消按鈕。
- 演練次數不限，但會消耗真實倒數時間與重排工時。
- 演練後只有倒下的骨牌維持倒下；門、柱子及其他積木保留原狀。
- 不提供自動復原、施工快照、舊版配置圖、幽靈位置提示或「重設全部」功能。
- 同一配置每次演練必須得到相同結果，避免隨機性掩蓋學生的規畫與修正。
- 演練失敗時，系統只播放結果與呈現倒下狀態；**不得**標示第一個中斷點或失敗原因。

### 9.2 小車與連鎖效果

- 測試與驗收時，系統以固定速度讓小車從起點前進。
- 小車依序通過兩門，僅碰倒指定起始骨牌後停止；不可視為推倒全部骨牌的工具。
- 骨牌的倒下與傳遞採規則判定，須檢查方向、相鄰距離、高度階梯與必經節點。
- 驗收動畫須清楚顯示小車、骨牌傳遞及最後狀態，讓小組可在討論時回顧。

### 9.3 正式驗收

- 正式驗收僅可執行 **1 次**。
- 學生可在時間未到前自行選擇送驗，不可事後撤回。
- 按下後立即：鎖定施工板、停止計時、擷取驗收前施工圖、執行動畫並判定結果。
- 驗收成功條件：小車通過兩門並觸發起始骨牌；S 路徑、8 層階梯與完整鑽石陣皆成功連鎖倒下。
- 驗收失敗時，結果頁才顯示第一個失敗原因；例如間距中斷、方向不符、階梯高度不符、未完成必經結構等。
- 驗收成功即為「專案成功」；不比較成本、剩餘時間或演練次數。

### 9.4 時間到期

- 若倒數歸零前尚未送交正式驗收，系統立即鎖定施工板並擷取當下施工圖。
- 結果固定為：`專案失敗：未在期限內送交正式驗收。`
- 不自動進行驗收動畫，不允許延時或補送。

## 10. 結果畫面與驗收 PDF

無論正式驗收成功、正式驗收失敗或時間到期，均進入結果畫面。結果畫面提供：

- 成功／失敗的明確結論。
- 驗收失敗時的第一個失敗原因；時間到期則顯示未送驗。
- 小組名稱。
- 遊戲開始時間與結束／到期時間。
- 總使用時間。
- 總花費、剩餘預算、採購次數與緊急採購費。
- 驗收前施工圖（正式送驗前快照；若未送驗則為時間到期快照）。
- 採購紀錄。
- `下載驗收 PDF` 按鈕。

驗收 PDF 至少包含以下欄位：

| 區塊 | 內容 |
| --- | --- |
| 基本資料 | 小組名稱、遊戲開始與結束／到期時間、總使用時間 |
| 專案結論 | 正式驗收成功／失敗；未送驗則標示期限到期 |
| 最終施工圖 | 送驗前或時間到期時的工地截圖 |
| 採購紀錄 | 每筆訂單的時間、材料、單買／10 入包裝、數量、材料成本、行政費、累計成本 |
| 資源摘要 | 總成本、剩餘預算、採購訂單數、演練次數（僅作回顧，不作計分） |

PDF 不可包含授權碼、需求釐清問題、教師回答或任何隱藏驗收規則。

## 11. 正式驗收標準

正式驗收僅能執行一次。小車從起點以固定速度前進，通過兩座門、碰倒起始骨牌後停止；S 型路徑、8 層階梯與完整菱形骨牌陣必須依序完成連鎖。以下項目必須全部符合，專案才算成功。

| 類別 | 正式驗收標準 | 判定方式 |
| --- | --- | --- |
| 兩座門 | 每座門皆為「兩柱一橫梁」的獨立積木結構，且小車能通過 | 3D 模型顯示門洞；規則引擎檢查左右支撐、橫梁、連通性與小車通道 |
| 門距 | 兩座門距離至少 10 cm | 以施工資料中的門洞中心或指定量測點計算 |
| 兩根柱子 | 位於門後、各自獨立，且高度大於 6 cm | 不可與門相連；最高高度至少 7 cm |
| 材料限制 | 門與柱子只使用積木；骨牌只用於連鎖 | 依物件類型與結構範圍檢查 |
| 起始觸發 | 小車通過兩門並碰倒起始骨牌 | 固定路徑動畫與規則判定一致 |
| S 型路徑 | 骨牌形成連續的 S 型傳遞，含至少兩次反向彎折 | 檢查平面座標、方向、相鄰距離與高度差 |
| 8 層階梯 | 骨牌階梯精確有 8 個高度層級 | 必須含高度 1 至 8；可中空，不要求實心 |
| 菱形骨牌陣 | 完整填滿的 10 × 10 菱形骨牌陣 | 10 列、共 60 枚；列數為 2／4／6／8／10／10／8／6／4／2 |
| 最終連鎖 | 所有任務指定骨牌都倒下 | 任一必經骨牌未倒下即失敗；額外未使用材料不影響結果 |
| 時間與送驗 | 必須在 60 分鐘內主動送交正式驗收 | 時間到未送驗即失敗，不自動驗收 |

驗收動畫為 3D 呈現，但結果完全由確定性規則引擎決定；相同配置必定得到相同結果。演練只顯示倒下狀態，不標示失敗原因；正式驗收失敗時才顯示第一個不符合的原因。

## 12. 內部驗收規則

程式應將「視覺呈現」與「驗收判定」分開實作。建議將每個關鍵條件寫成獨立、可測試的規則：

1. `validateGates()`：確認 2 個門存在且兩門距離符合規範。
2. `validatePillars()`：確認 2 根柱子皆由積木構成，且高度大於規範。
3. `validateMaterialUse()`：門、柱子未使用骨牌；骨牌未被當結構材料。
4. `validateSPath()`：確認 S 型路徑、骨牌方向與連鎖距離。
5. `validateStairs()`：確認剛好 8 層且連鎖方向／高差可傳遞。
6. `validateDiamond()`：確認完整填滿的菱形模板與所有骨牌均可被連鎖觸發。
7. `validateCarRoute()`：確認小車可通過兩門並撞到指定起始骨牌。
8. `runAcceptance()`：依固定順序執行上述規則與動畫；第一次不合格即為結果頁的失敗原因。

學生演練時可使用相同判定引擎，但不得回傳規則名稱、座標、失敗原因或中斷點；只呈現動態結果。正式驗收才回傳第一個失敗原因。

## 14. 技術實作建議

| 面向 | 建議 |
| --- | --- |
| 前端 | React + TypeScript + Vite，靜態輸出至 GitHub Pages。 |
| 拖放 | dnd-kit 或原生 Pointer Events；須支援格點吸附、旋轉、堆疊。 |
| 3D 畫面渲染 | React Three Fiber + Three.js；建立積木、骨牌、小車、施工板與可控制鏡頭。 |
| 互動控制 | 使用射線投射選取物件；支援拖放、90 度旋轉、堆疊、鏡頭旋轉、縮放與平移。 |
| 規則引擎 | 獨立於 3D 渲染；以格位、旋轉、占地與高度計算驗收結果，再驅動對應的 3D 動畫。 |
| 本機保存 | localStorage；每次採購、放置、移除、演練後自動儲存。 |
| 圖片快照 | 將施工板轉為 PNG，供結果頁與 PDF 使用。 |
| PDF | jsPDF 搭配 html2canvas，於瀏覽器直接產生與下載。 |
| 可測試性 | 驗收規則與 UI 分離，對每一條驗收規則撰寫單元測試。 |

GitHub Pages 為純靜態網站，因此不適合把 `car666` 當成真正的安全機制；它的功能是模擬「學生需主動向客戶取得測試資源」，而非防止學生在程式碼中找到字串。課堂管理仍以教師現場授權為主。

## 15. 上線前驗收與試玩

### 14.1 功能驗收

- [ ] 輸入小組名稱後才可開始，且正確記錄開始時間。
- [ ] 倒數為 60 分鐘；重整頁面後能從 localStorage 回復。
- [ ] 商店價格、10 入折扣、前 3 次免費與第 4 次起 50 點行政費正確。
- [ ] 不可退款；移除板上物件只回庫存、不退還成本。
- [ ] 未授權前不顯示演練與正式驗收。
- [ ] 授權後可拖放靜態小車；演練與驗收時才自動前進。
- [ ] 演練後僅倒下骨牌留在倒下狀態，且不能一鍵復原。
- [ ] 演練不顯示失敗原因；正式驗收失敗才顯示第一個失敗原因。
- [ ] 正式驗收只能執行一次，送驗後立即鎖定。
- [ ] 時間到期不自動送驗，直接判定未送驗失敗。
- [ ] 結果 PDF 包含施工圖與採購紀錄，但不含授權碼與教師問答。

### 14.2 課堂試玩

正式課程前，建議找 2–3 組進行 60 分鐘試玩，特別觀察：

1. 學生是否自然注意到需要向教師詢問需求與取得小車。
2. 1,000 點預算是否讓可行方案有空間、但不會太寬鬆。
3. 3 次採購是否足以引出「先規畫」與「補貨代價」的差異。
4. 演練、扶正與重排是否確實消耗足夠時間，形成不演練的誘惑。
5. 最終成功率是否約落在「有規畫與演練的組別可成功，但不保證人人成功」的難度。
6. 驗收動畫與失敗訊息是否足以支持課後討論，但不會在演練階段變成解答。
